# C 题建模构建模块设计

> 状态：已实现。调度见 `AGENTS.md` 与 `Workflow/README.md`，团队配置见 `Workflow/modeling-team.json`，角色 prompt 位于 `prompts/modeling/`，开放模板位于 `templates/modeling/`。本模块只负责把冻结题意、路线和数据接口变成可运行候选，并交给后续独立验证。

## 1. 模块目标与边界

建模构建不是再次猜题，也不是看到结果后不断换算法。它负责把前面已经形成的工作解释转化为明确、可运行、可追溯的数学与计算对象：

- 每问的目标量、状态量、决策量、约束和输出对象；
- 数学假设、公式、题间接口和适用边界；
- 可解释 baseline、暂定主路线与必要的存活挑战路线；
- 可复现代码、配置、运行记录和候选结果；
- 供验证模块审查的脆弱假设、失败记录与待证主张；
- 供论文模块使用的工程方法文稿，而不是正式论文正文。

入口至少包括：

- `synthesis/problem-baseline.md`；
- `routes/route-handoff.md`；
- `data/data-handoff.md`；
- 数据工程明确允许使用的数据版本和分析视图；
- 与当前问题直接相关的原始 memo、少数意见和重开条件。

模块终点建议为 `modeling/model-handoff.md`。交接中的模型、结果和结论全部是**待独立验证候选**，不能直接写成已确认论文结论。

本模块不负责：

- 重新解释原始题目并静默覆盖题意基线；
- 直接修改 Canonical 数据或改写数据契约；
- 正式的泛化、稳健性、敏感性、泄漏、统计显著性或独立复现审查；
- 把候选模型宣布为最终模型；
- 论文级绘图、答卷生成或正式论文写作。

允许实现者做最低限度的构建自检，例如维度一致、代码能运行、求解器状态可记录、明显约束没有被程序遗漏。这些只证明“构建物可运行”，不等于正式验证。

## 2. 为什么按问题纵向构建

C 题通常不是一组互不相关的模型。上游问题可能产生状态估计、参数、评分、分类、预测或候选集合，随后被下游优化、决策或评价直接消费。因此采用：

> 共享建模基础集中维护，按题间依赖逐问形成纵向切片。

每个问题切片都应从数据接口走到候选结果：

```text
题意与路线接口
→ 数学规格
→ 计算方案
→ baseline
→ 主候选/必要挑战候选
→ 候选结果与工程文稿
→ 向下一问和验证模块交接
```

Leader 先画问题依赖图：

- 无依赖问题可以并行，但必须拥有独立写入目录；
- 有依赖问题按接口顺序推进；
- 下游若使用尚未验证的上游结果，必须记录上游版本和失效传播关系；
- 共享参数、公共状态或公共代码只有一个所有者，不允许多个实现者同时改写。

## 3. Agent Team

继续采用当前主 Agent 担任唯一 Leader、最多 3 个并发 subagent。不是每个问题都固定占满全部角色；角色数量由结构风险和计算复杂度决定。

### 3.1 Leader

Leader 负责：

- 从三份上游交接建立问题依赖图与逐问构建顺序；
- 冻结当前问题允许使用的数据、目标、约束和题间接口；
- 创建开放 task brief，隔离建模规格、计算可行性和结构挑战视角；
- 综合形成当前问题的建模构建合同；
- 指定共享代码和每问代码的唯一实现所有者；
- 管理 baseline、主候选、挑战候选、运行版本和失效传播；
- 处理数据变更请求、路线重开和问题间接口冲突；
- 最后形成模型交接，不替代后续独立验证者宣布模型可信。

Leader 不得先报模型名让其他角色补理由，也不得用运行成功、指标较好或实现者自评代替正式验证。

### 3.2 数学规格架构师

把题意、路线和数据接口转成可计算的数学规格，但不编写正式实现。

最低责任：

- 定义集合、索引、变量、参数、状态量、决策量和输出；
- 写明目标函数、约束、状态转移、观测关系或统计估计对象；
- 逐项对应题面要求和数据字段，不凭空制造标签或约束；
- 说明识别条件、可行性条件、初边值、边界条件和量纲；
- 明确 baseline、主结构和仍存竞争结构的本质差异；
- 写清本问结果如何被下一问消费。

### 3.3 计算路径规划师

从数值、算法和工程角度判断数学规格怎样落地，但不抢占共享实现所有权。

最低责任：

- 分析问题规模、复杂度、稀疏性、凸性、离散性、随机性和数值稳定性；
- 比较解析、数值、统计学习、仿真或优化求解路径；
- 给出 baseline 与主候选的最小可运行顺序；
- 说明求解器、依赖、初始化、终止条件、随机性和资源风险；
- 识别无法由当前数据或时间预算支持的路线；
- 规划统一输入/输出接口和可追溯运行记录。

### 3.4 结构挑战者

在看到实现结果前攻击当前建模结构，避免计算成功掩盖结构错误。它不是后续正式验证者。

最低责任：

- 寻找更简单但足以回答题目的 baseline；
- 攻击目标、约束、独立性、平稳性、线性、分布、因果或最优性假设；
- 检查路线是否遗漏反馈、层级、时间、空间或题间依赖；
- 指出哪种最小反例会让当前结构失效；
- 判断存活挑战路线是否值得构建，还是只需记录为验证假说；
- 给出结构切换触发器，而不是堆砌更复杂算法。

### 3.5 模型实现者

根据 Leader 冻结的构建合同，成为当前问题或共享建模内核的唯一实现所有者。

最低责任：

- 先实现可解释 baseline，再实现主候选和被明确保留的挑战候选；
- 保持统一数据入口、配置、输出和题间接口；
- 实现公式、约束、参数、求解流程和必要的工程自检；
- 保存运行命令、环境、随机种子、求解器状态和候选结果表；
- 记录失败尝试、未收敛、不可行、数值异常和临时妥协；
- 同步维护模型方法工程文稿，不直接写正式论文。

实现者不能修改数据工程共享层，不能用结果倒推题意，也不能删除失败记录只保留最佳结果。

### 3.6 构建结果诊断者

这是按异常触发的新 subagent，不是每次运行都固定创建，也不是后续正式验证者。它只回答“当前结果为什么不符合预期，下一次最有区分力的调整是什么”。

最低责任：

- 区分实现错误、数值/求解问题、模型结构问题、数据接口问题、评价口径问题和正常但不理想的结果；
- 同时检查结果过差、异常地好、违反常识、约束失效、输出错位和下游无法消费；
- 对每个解释给出运行/代码/数据证据、可反驳观察和最小判别动作；
- 指明建议调整属于哪一级、哪些内容必须冻结、会使哪些运行失效；
- 不直接改代码、数据、规格或结果，不以一次指标决定最终路线。

高影响异常由新的诊断者独立看待；低影响、可定位的工程错误不为形式完整额外创建 Agent。

## 4. 调度主链：固定外框与触发式迭代内核

建模结果不可预先知道，因此不能把 M3/M4 写成一次通过的直线。固定的是责任、上下文和版本；动态的是实际需要多少次诊断与调整。

```text
M0 Leader 接收与问题编排
→ M1 三视角构建前分析
→ M2 Leader 冻结构建合同、开发反馈和调整权限
→ M3 baseline 最小贯通
→ M4 观察—诊断—裁决—调整—重跑循环
→ M5 跨问接口装配
→ M6 Leader 模型交接
```

### M0：Leader 接收与问题编排

Leader 读取题意、路线和数据交接，先完成：

1. 逐问列出答案对象、输入数据视图和允许使用的信息时点；
2. 画出问题依赖图、共享建模对象和失效传播路径；
3. 标出可并行问题、必须串行问题和共享代码所有者；
4. 为每问划分构建时可见的开发反馈，以及必须留给后续独立验证的信息；
5. 选择完整或精简模式，为 M1 角色创建隔离 task brief。

此时不写最终模型公式，不以算法名替代问题结构，也不提前查看为了独立验证而保留的信息。

### M1：三视角构建前分析

完整模式并行创建 3 个新的隔离 subagent：

1. 数学规格架构师；
2. 计算路径规划师；
3. 结构挑战者。

三者读取相同冻结交接和自己的 brief，首轮不读取彼此报告或 Leader 模型倾向。建议输出：

- `modeling/specs/qN-formulation.md`；
- `modeling/plans/qN-computation-plan.md`；
- `modeling/challenges/qN-structural-challenge.md`。

如果冲突会改变变量、目标、约束、评价口径或跨问接口，Leader 可以复用原角色做一次定向澄清。没有实质冲突时不增加固定答辩波次。

### M2：Leader 冻结构建合同与调整包络

Leader 综合 M1 原报告，形成当前问题可执行但可回滚的 `modeling/specs/qN-build-contract.md`。除数学规格外，必须在第一次运行前写清：

- **开发反馈**：构建阶段允许看的数据、指标、约束残差、已知边界样例和定性现象；
- **保留信息**：留给后续独立验证、不得用于反复调参或选模型的信息；
- **结果预期画像**：不是目标分数，而是合理输出的对象、范围、符号、数量级、形状、约束状态和下游接口；
- **比较基准**：冻结 baseline 的规格、数据和输出口径；
- **调整包络**：实现者可以自行调整的配置范围、需要 Leader 裁决的结构变化、必须退回上游的变化；
- **候选与分支预算**：当前主候选、唯一活跃挑战候选、单轮允许改动和计算/时间预算；
- **停止与重开信号**：什么现象继续局部调整，什么现象重开 M2、数据、路线或题意。

合同不是正确性门禁，也不要求预知正确结果。它冻结的是比较口径和修改权限，防止看到结果后任意改目标、数据、指标和约束。

### M3：baseline 最小纵向贯通

Leader 创建 1 个新的模型实现者，先贯通：

```text
冻结数据视图
→ 统一读取接口
→ 最简单可解释 baseline
→ 标准候选结果表
→ 下一问可消费接口
→ 运行与方法记录
```

baseline 不要求效果最好，但必须给后续调整提供稳定参照。实现者先单独写 run intent，记录本次目的、允许使用的开发反馈、预期观察和冻结项，再运行；不能看到结果后补写“原本就想验证什么”。

首次结果无论好坏都落盘。特别是异常地好也要进入诊断，因为它可能来自泄漏、目标穿越、错误切分、重复样本或评价口径错误。

### M4：触发式构建调整循环

M4 不是“继续调到满意”，而是重复以下五个动作：

#### M4A 观察与归因请求

原实现者为当前运行写开放 iteration memo，至少回答：发生了什么、与 baseline/预期画像差在哪里、使用了哪些开发反馈、当前有哪些竞争解释、建议调整什么、哪些内容保持冻结。run intent、原始运行产物和事后解释必须能分开引用，避免把事后解释伪装成运行前预期。

以下任一情况触发独立诊断：

- 主候选明显弱于 baseline，且不是已知取舍；
- 输出对象、单位、粒度、范围或符号与题意/接口不符；
- 约束违反、不可行、未收敛、数值爆炸或资源超预算；
- 轻微配置变化导致结果大幅翻转；
- 结果异常地好、几乎完美或与数据难度不相称；
- 下游问题无法消费当前结果；
- 为继续改进必须改变目标、数据、标签、评价口径或核心结构；
- 实现者无法区分两个高影响失败解释。

#### M4B 新诊断者独立分析

触发时创建新的构建结果诊断者。第一轮只允许它读取冻结合同、run intent、相关代码、原始运行日志/结果和 Leader 根据预设信号写出的中性触发说明；不得先读实现者的事后归因和建议改法。它不修改文件，输出建议为 `modeling/diagnostics/qN-iteration-K-diagnosis.md`。

诊断者必须区分：

1. 实现缺陷；
2. 数值、求解器或资源问题；
3. 超参数/算法细节问题；
4. 模型结构或假设问题；
5. 数据接口、可用时点或目标构造问题；
6. 评价口径与题目回答目标不一致；
7. 结果本身合理，只是没有达到未经证据支持的主观期待。

诊断不能只说“换一个模型”。它要给出最便宜、最有区分力的下一动作及其预期观察。

#### M4C 原实现者回应

诊断 memo 落盘后，Leader 才交换诊断者与实现者的两份解释。复用原模型实现者做一次集中回应：接受、用证据反驳、保留分支或请求上游重开。实现者提出下一轮 adjustment card，但在 Leader 裁决前不修改冻结对象。

低影响且可定位的代码错误可以由实现者直接记录并修复；不得为了形式完整强制创建诊断者。

#### M4D Leader 裁决调整级别

Leader 不投票，按证据区分调整层级：

- L0/L1：允许同一实现者局部修正；
- L2：修订构建合同后再实现；
- L3：暂停本问，向数据、路线或题意阶段发变更请求；
- 暂不可判：保留主/挑战两条分支，交给后续验证；
- 没有高价值下一动作：冻结当前候选并停止继续搜索。

#### M4E 单假设调整与重跑

一次迭代只改变一个主要诊断假设，或一组不可分割的联动修改。先写预期观察、冻结项、影响范围和回滚点，再由原实现者修改、重跑并生成新版本。

若新证据推翻诊断，回滚该版本而不是继续叠加补丁。若结果仍差但失败类型已经改变，重新进入 M4A，不默认沿用上轮解释。

主候选与必要挑战候选都使用同一循环，但同一问题默认只维护一个主分支和一个实质挑战分支。新增第三条活跃分支必须由 Leader 说明它能区分什么高影响结构，以及为何现有两条不足。

### M5：跨问接口装配

每问得到可运行候选后，Leader 组织题间接口装配，但不亲自编写适配代码：

1. 复用上游和下游原实现者，各自写生产方/消费方接口说明和无法消费点；
2. 无需改代码时，Leader 只综合当前接口版本与失效传播；
3. 需要共享适配代码时，Leader 从相关原实现者中指定一个唯一接口集成所有者，其他实现者只读并提供意见；
4. 接口集成所有者只能修改 brief 明列的接口路径，不能借机改变上游数学含义或下游目标。

装配重点是确认：

- 上游输出的对象、主键、粒度、单位和时间能否被下游读取；
- 下游是否依赖某个尚未验证的上游版本；
- 上游候选变化会使哪些下游运行失效；
- 共同变量、参数和代码是否只有一个当前版本；
- 为了接通接口是否发生了未授权的聚合、插值、标签制造或口径变化。

接口问题优先回到产生它的最早问题，不在下游用适配代码掩盖。

### M6：Leader 模型交接

Leader 汇总规格、计算计划、结构挑战、构建合同、全部 iteration memo、诊断/回应、代码、候选结果和工程文稿，形成 `modeling/model-handoff.md`。

交接至少包括：

- 当前问题依赖图、执行顺序和版本关系；
- 每问 baseline、主候选、存活挑战候选及其未决差异；
- 数据版本、代码入口、环境、配置和结果路径；
- 每次关键调整的诊断、冻结项、修改、结果和回滚关系；
- 候选结果对象、单位、粒度、时间和题间接口；
- 失败运行、不可行结构、异常地好/差的结果和实现妥协；
- 已消耗的开发反馈与明确未用于调整的保留信息；
- 后续验证必须优先攻击的假设、分支和结果；
- 可供论文使用的工程材料位置，以及不能升级为论文事实的候选主张。

M6 完成后建模构建模块停止，等待独立验证模块接手。

## 5. 调整等级、权限与约束

### 5.1 先定义“结果哪里不好”

“效果不好”不能只等于某个分数低。每次诊断至少从以下角度描述偏差：

| 观察维度 | 典型现象 | 首要怀疑 |
|---|---|---|
| 执行状态 | 报错、超时、未收敛、不可行、内存超限 | 实现、求解器、规模或规格可行性 |
| 数学一致性 | 量纲错误、违反约束、守恒失败、边界行为错误 | 公式映射或实现缺陷 |
| 回答对齐 | 输出对象、总体、粒度、单位或时间不回答题目 | 规格、数据接口或评价口径 |
| 相对表现 | 主候选低于 baseline，复杂度增加却没有相应信息收益 | 结构、参数、实现或不必要复杂化 |
| 形态与常识 | 符号、趋势、范围、排序或策略明显反常 | 数据、假设、目标或实现 |
| 稳定迹象 | 无关紧要的初值/配置变化导致巨大翻转 | 数值或不可识别性；正式稳健性仍留后续验证 |
| 异常优秀 | 近乎完美、远超合理上限或与任务难度不符 | 泄漏、重复、错误切分、未来信息或指标实现 |
| 题间消费 | 下游无法读取或需要临时改口径才能使用 | 上游接口或问题依赖设计 |

这些是诊断镜头，不是统一阈值或语义硬门禁。具体问题在 M2 预先写自己的结果预期画像和可观察失败信号。

### 5.2 四级调整

| 等级 | 可改变内容 | 不可改变内容 | 决策与执行 |
|---|---|---|---|
| L0 实现修复 | 索引、公式翻译、维度、读写、日志、明显代码错误 | 数学规格、数据版本、评价口径 | 原实现者可修复，但必须记版本、证据和影响 |
| L1 合同内计算调整 | 合同预授权范围内的初始化、容差、求解器参数、迭代预算、随机种子策略和算法实现细节 | 目标、约束含义、样本总体、标签、数据切分、结果口径 | 原实现者提出并执行；超出预授权范围由 Leader 先裁决 |
| L2 模型结构调整 | 状态关系、函数形式、目标/约束表达、模型特定特征、候选族或结构分支 | 题意对象和共享数据契约不得静默变化 | Leader 重开 M2；数学规格/结构角色定向复核，构建合同升版后由原实现者实施 |
| L3 上游调整 | 目标构造、标签/proxy、总体、Canonical 数据、题间接口、题意或路线 | 实现者无权直接修改 | 暂停本问，发证据化变更请求到数据、路线或题意阶段 |

判断等级看“修改会改变什么含义”，不看代码改动行数。改一行目标函数可能是 L2/L3；大规模重构若数学对象不变仍可能只是 L0。

### 5.3 adjustment card

每次非平凡调整先写开放 Markdown adjustment card。以下是最低责任，不是字段白名单：

- 哪个运行出现了什么观察，证据在哪里；
- 与冻结 baseline、预期画像或接口的差异是什么；
- 当前有哪些竞争失败解释，为什么优先处理其中一个；
- 本轮主要改变什么，属于 L0/L1/L2/L3 哪一级；
- 哪些数据、目标、约束、评价、接口和版本保持冻结；
- 预期出现什么可区分观察，什么结果会反驳本轮诊断；
- 修改影响哪些文件、候选、问题和下游运行；
- 时间/计算预算、回滚位置和停止条件；
- 运行后实际发生什么，下一步是保留、回滚、再诊断还是上游重开。

禁止先连续尝试多种修改，最后只为成功版本补一张卡。失败调整和无改善结果同样保留。

### 5.4 构建阶段不可突破的约束

1. **开发反馈与保留信息隔离**：用于调节模型的信息在 M2 预先声明；留给独立验证的信息不得因“效果不好”提前打开。
2. **baseline 口径冻结**：baseline 可修复错误，但不得为衬托主候选而降低质量、换数据或换评价口径；修复后所有比较重新标记版本。
3. **单次主要假设**：一轮只改变一个主要诊断假设，避免结果变化无法归因；不可分割的联动修改要说明因果关系。
4. **数据边界不反向漂移**：模型 Agent 不修改 Canonical 数据，不为了分数改变总体、标签、缺失定义、时间窗口或样本切分。
5. **评价口径不追着结果变**：指标、约束惩罚、排序规则和结果汇总方式若要变化，必须先解释它为何更符合题意并升级到相应层级。
6. **单一实现所有权**：同一问题和共享内核仍由原实现者修改；诊断者只读，避免多个 Agent 同时打补丁。
7. **版本与失效传播**：任何调整产生新版本，旧版本保留；上游变化必须标记哪些下游运行、结果和文稿失效。
8. **不按单指标自动选胜者**：运行结果用于产生证据，不直接裁决最终模型；复杂度、解释性、约束、接口和失效边界一起交给验证模块。
9. **不为耗尽算力而搜索**：超参数搜索、随机试错或模型堆叠必须对应明确诊断，不得把剩余时间自动转成无界搜索。

### 5.5 继续、分支、停止与升级

继续一轮调整，需要至少满足：存在会影响答卷或下游的高价值不确定性，并且有成本可接受、能区分竞争解释的下一动作。

保留主/挑战双分支，适用于两个结构都有依据、当前开发反馈无法可靠区分，而选择会改变答案的情况。此时不要强行在构建模块选胜者。

停止继续搜索，适用于：

- 剩余差异只是在同一口径上的边际指标波动；
- 下一步只会增加复杂度，却不能区分任何高影响解释；
- 继续选择需要使用保留验证信息；
- 已达到预先分配的时间/计算预算，且不存在会阻止交接的实现缺陷；
- 当前不确定性本质上需要独立复现、稳健性、敏感性或外部证据判断。

立即升级而不继续调参，适用于：目标不可构造、合理口径改变答卷、必须制造标签、数据时点产生泄漏、核心约束与题意冲突、题间接口无法在冻结含义下接通。

停止是把未决问题完整交给验证或上游，不是宣称模型已经足够好。

目录表达所有权和血缘，不是固定语义 schema。每个角色交付开放 Markdown，并可增加未预见章节。JSON/YAML 可以记录运行配置、路径、版本、参数和状态，但不裁决假设、模型适用性或路线优劣。

建议的核心开放文稿：

- 问题依赖图与逐问执行计划；

- 每次构建运行 memo；
- 触发式诊断、原实现者回应与 adjustment card；
- 候选结果索引；
- 模型方法工程文稿；
- 模型交接。

## 7. baseline、主候选与挑战候选

三类构建物承担不同责任：

- **baseline**：回答“最简单的完整方案能做到什么”，提供可解释参照和接口样例；
- **主候选**：实现路线交接中当前证据最支持的结构；
- **挑战候选**：只挑战会改变答案的核心结构假设，不用复杂度或模型名制造差异。

不是每题都必须实现三个模型。以下情况可以只保留 baseline 与主候选：挑战结构无法由现有数据区分、实现成本显著超出价值，或差异只在算法细节而不改变答卷。理由写入构建合同和模型交接。

同样，结果较差不能自动淘汰候选：可能是实现错误、数据接口错误、参数配置问题或结构确实不适用。正式裁决留给后续独立验证。

## 8. 运行与结果留档

每次有意义的构建运行至少记录：

- 唯一运行标识、问题编号和目的；
- source/data/code/config 版本；
- 输入视图、字段、样本范围和时间边界；
- 本轮实际使用的开发反馈及没有打开的保留信息；
- 模型规格与候选名称；
- 参数、初始化、随机种子、求解器和资源环境；
- 运行状态、耗时、收敛/可行状态和异常；
- 机器可读候选结果表与题间接口产物；
- 观察、失败原因、未决问题和下一步；
- 对应 adjustment card、诊断报告、父运行和回滚关系；
- 哪些内容只是实现者解释，尚待独立验证。

不要只保存 Notebook 最后一次状态、截图或手抄结果。精确数字必须能回到运行记录和机器结果文件。

## 9. 为论文保留工程文稿

模型实现者在构建同时维护每问的模型方法工程文稿，建议路径：

`modeling/paper-notes/qN-model-method-note.md`

至少保留：

- 问题目标与建模对象；
- 符号表、变量、参数、单位和索引；
- 假设及题面、数据或路线依据；
- 公式、目标、约束、状态转移和边界条件；
- baseline、主候选、挑战候选及选择理由；
- 算法/求解流程、伪代码、参数和环境；
- 与上游数据、下游问题的接口；
- 候选结果索引、失败记录和适用边界；
- 需要后续验证的主张和不能过度表述的内容。

工程文稿不追求论文语言。原则仍是：边构建边记录，验证稳定后形成章节材料包，最后再统一写论文。

## 10. 完整模式与精简模式

出现以下任一情况时采用完整模式：

- 多问题强依赖或共享状态/参数；
- 优化、仿真、动态系统、时空模型或组合决策；
- 目标/约束/识别条件存在实质竞争解释；
- 主路线和挑战路线会产生不同答卷；
- 求解规模、可行性、数值稳定性或计算预算有风险；
- 上游候选结果会显著影响下游模型。

只有在单问或弱依赖、数学对象清楚、算法路径直接、规模小且没有实质结构分支时采用精简模式。精简模式可以由 Leader 完成问题编排，创建 1 个规格角色和 1 个实现者；若出现第 4 节所列高影响触发信号，仍创建新的结果诊断者。baseline、adjustment card、运行记录、工程文稿、模型交接和后续独立验证入口不能省略。

精简模式不是省略追溯，也不能由同一个实现者把自己的结果直接宣布为最终结论。

## 11. 变更请求与局部回滚

- 数据字段或分析视图不足：向数据工程提交明确变更请求，说明需要什么、为何需要、影响哪些问题；模型实现者不直接改共享数据。
- 数学规格与路线交接冲突：回到 M2，必要时重开路线竞标。
- 目标、总体或答卷对象发生变化：重开最早受影响的题意判断。
- 代码或求解实现错误：在当前问题 M3/M4 修订，保留旧运行。
- 共享内核变化：标记所有受影响问题和需要重跑的候选结果。
- 上游问题结果版本变化：按问题依赖图使相关下游运行失效，不全盘重做无关问题。
- 后续验证推翻候选：验证模块发回证据化变更请求，再局部进入 M2、M3 或 M4。

任何重开都保留旧规格、代码、配置、运行、候选结果和工程文稿，并明确当前采用版本。

## 13. 停止边界

本模块形成 `modeling/model-handoff.md` 后停止。它交付的是：可运行候选模型、候选结果、完整工程血缘和明确待验证问题。

下一模块负责独立验证。未经该模块审查，建模构建产物不得被标记为最终模型、稳健结论或可直接写入论文的已确认主张。
