# C 题独立模型验证模块

> 状态：已实现。调度见 `AGENTS.md` 与 `Workflow/README.md`，机械配置见 `Workflow/validation-team.json`，角色 prompt 位于 `prompts/validation/`，开放模板位于 `templates/validation/`。

## 1. 目标与边界

本模块接收 `modeling/model-handoff.md` 中的可运行候选，用独立证据判断：

- 数学定义、代码、配置与求解过程是否一致；
- 候选结果是否可复现，是否存在泄漏、虚假可行或不稳定；
- 哪个具体主张可以引用，适用范围和失效条件是什么；
- 上下游题间接口是否可以按版本、粒度、单位和时间真正消费；
- 发现问题后应返回数据、建模合同、实现、路线还是题意阶段。

入口至少包括模型交接、formulation、build contract、代码/config/run/结果、题间接口、D4 数据复核、已用开发反馈、未打开保留信息和官方交付要求。

终点为 `validation/validation-handoff.md`。它授权后续可使用的结果和主张，但不生成论文图、答卷或正文。

验证者不得继续调参、静默修改 `data/` 或 `modeling/`、更换指标/验证集以追求“通过”，也不宣称模型无条件正确。

## 2. 设计原则

### 2.1 按主张裁决

验证单位是“主张—结果—模型—证据—适用边界”，不是整个模型的通过/不通过标记。同一模型可能足以支持方向性结论，但不足以支持精确数值或因果结论。

### 2.2 固定证据纪律，动态选择 probe

统计学习、时序、优化、仿真、评价和网络模型的失效方式不同。工作流只固定独立性、读写权、事前意图、原始输出、回应与裁决顺序；具体 probe 由当题高影响失效机制决定。

### 2.3 所有权不混合

验证者可以在 `validation/probes/` 下写包装、检查和对照代码，但不得修改原数据或模型实现。需修正时返回原 owner，旧版本和失效传播必须保留。

### 2.4 验证信息暴露不可逆

一旦某份保留证据被反馈给 builder 并用于修正，它就成为开发信息，不能继续充当独立 holdout。复验需要新切片、嵌套设计、滚动回测或其他独立证据。

## 3. Agent Team

当前主 Agent 担任唯一 Validation Leader，最多同时运行 3 个 subagent。

- **Validation Leader**：冻结验证对象、隔离上下文、综合风险、授权 probe、维护暴露账本、按主张裁决并路由局部回滚。
- **数学—实现审计者**：核对题意、变量、公式、目标、约束、量纲、边界、代码、配置和求解状态。
- **实验证据审计者**：检查泄漏、切分、baseline 公平性、指标、不确定性、稳健性和主张证据负担。
- **复现—接口审计者**：从冻结入口复跑，核对环境、随机性、结果表、题间消费和官方交付。
- **整体题链审计者**：强题间依赖时条件创建，检查版本、粒度、单位、时间、不确定性传播和整体答案。
- **原 owner 回应**：验证证据落盘后复用原 model/data builder，只做接受、证据化反驳、保留分支或修正影响说明。

## 4. V0–V6 固定外框

```text
V0 验证对象与保留信息冻结
→ V1 三视角隔离审查
→ V2 Leader 验证议程
→ V3 定向 probe
→ V4 原 owner 证据回应
→ V5 Leader 主张裁决、局部回滚或复验
→ V6 整体题链审查与验证交接
```

### V0：验证冻结

Leader 建立 `validation/scope/validation-map.md` 和 `validation/scope/exposure-ledger.md`，逐问记录答案对象、候选主张、证据链、高风险假设、已用开发反馈、未打开保留信息和失效传播。此时不执行新试验。

### V1：三视角隔离审查

完整模式创建三个新 subagent。三者首轮不读 peer 报告、Leader 根因倾向或 builder 新辩护。每份报告必须连接观察事实、竞争解释、影响、反例和最小区分动作。

### V2：验证议程

Leader 保留全部原报告和少数意见，按对答案/主张的影响、虚假优秀风险、题间传播、probe 区分力、成本和 holdout 消耗产生 `validation/dockets/qN-validation-docket.md`。不投票，不为形式完整穷举所有参数。

### V3：定向 probe

复用提出问题的 auditor，先写 `probe-intent.md`，事先冻结竞争解释、数据、模型、指标、对照、预期观察、暴露和停止线，再在唯一 `validation/probes/PROBE-ID/` 中运行。原始输出、失败和不可判结果都保留。

### V4：原 owner 证据回应

probe report 落盘后才复用原 owner。原 owner 可以接受、证据化反驳、保留竞争解释或说明修正影响，但 Leader 裁决前不得修改。

### V5：主张裁决与回滚

Leader 对具体主张记录：可引用、有条件可引用、暂不可引用、证据反驳或上游失效。回滚路由为：

- 索引/文档缺口：建模交接；
- 合同内实现或配置问题：M3/M4；
- 模型结构、目标或约束问题：M2；
- 字段、总体、时点或目标构造问题：D0–D4；
- 路线不成立：L2；
- 题意或问间关系错误：L1 或更早。

修正后只重验受影响主张及下游。若 builder 已看到原 holdout，必须先标记已消耗，再设计新独立证据。

### V6：整体题链与交接

强题间依赖时创建新整体题链审计者，检查 producer–artifact–consumer 版本、粒度、单位、时间、总体、不确定性传播和官方交付。Leader 最后写 claim-evidence map 和 `validation/validation-handoff.md`。

## 5. V3–V5 动态内核

只在“会改变答卷或论文主张的高价值不确定性 + 可负担且有区分力的下一动作”同时存在时继续。若只剩不改变主张的差异、只能反复消耗同一 holdout、无区分证据、预算不足或已明确属于上游责任，就限制主张、发起回滚或保留未决，不伪造共识。

## 6. 条件化验证视角

| 模型类型 | 优先攻击 |
|---|---|
| 回归/分类/机器学习 | 泄漏、切分、不平衡、校准、baseline、特征可用时点和外推 |
| 时间序列 | 滚动验证、未来信息、趋势/季节和预测跨度 |
| 优化 | 可行性、约束遗漏、量纲、上下界、求解容差、整数性和多解 |
| 仿真/动力系统 | 初边值、守恒量、步长收敛、随机重复、事件逻辑和长期稳定 |
| 综合评价/排名 | 归一化、权重、单调性、排名翻转、缺失和尺度变化 |
| 聚类/降维 | 标准化、簇数/维数、初始化稳定、可解释性和结构真实性 |
| 空间/网络 | 拓扑、空间泄漏、自相关、边界效应和连通性 |
| 多问级联 | 版本、接口、误差传播、上游翻转和下游可消费性 |

这些是视角库，不是每题全做的 checklist。

## 7. 完整与精简模式

完整模式用于学习、时序、优化、仿真、时空/网络、综合评价、强题间依赖、proxy/泄漏风险、异常优秀结果或高影响 holdout，执行 V1 三路和必要 V6 独立审查。

精简模式仅限数学对象清晰、确定性强、单问/弱依赖且无实质分支。可只创建数学—实现和复现—接口两个 auditor，但不能取消 validation map、exposure ledger、独立 probe、主张裁决、回滚入口和最终交接。出现高影响泄漏、结构或题间风险时立即升级。

## 8. 工程产物与停止边界

运行目录使用 `validation/scope/`、`reviews/`、`dockets/`、`probes/`、`responses/`、`decisions/`、`interfaces/`、`claims/` 和 `change-requests/`。语义判断写开放 Markdown；JSON/YAML 只保存路径、哈希、版本、参数、随机种子和状态。

`validation/validation-handoff.md` 完成后立即停止。后续模块只能使用交接授权的结果、主张和条件，不得从建模目录自行挑选更好看的运行。
